# 下一轮节点退出系统：建议方案，尚未执行

本文是下一轮的工作建议。本轮六例30组比较已完成，五组均6/6成功；交接相对直接删除的总token仅低3.12%，且四例更贵。完整结果见实验报告。以下是建议，尚未实现或启动新实验。

## 已经知道什么

- S5 展示了显式订阅依赖：只有订阅 owner 能处理事件，退出前转交订阅会改变后续执行能力。这个限制由该实验环境明确设定，不能直接推广到所有多 agent 系统。
- 已核实的 WorkBench 日历结果表明，直接删除后，已有权限的备份成员也能查询公共数据、恢复工作。完整交接需要和这种正常恢复方式比较。
- 当前 WorkBench 交接主要修改中央 assignment owner，并保留公共 progress。它还没有迁移 agent 私有记忆、未完成承诺或真正的待办队列；候选和初始拓扑也是固定的。
- 原生全局 evidence digest 会向其他成员暴露跨节点历史。若下一轮研究私有状态，必须先修正信息可见性；否则“没有交接”的组也可能已经得到交接内容。

因此，下一轮优先回答一个更具体的问题：**当一个看起来已经闲下来的成员仍持有待办、处理位置或审核职责时，显式交接是否比保留它或让剩余成员自行恢复更可靠、更省？**

## 小范围任务：建议先做三组成对案例

每组使用同一业务请求，仅改变一个影响退出的条件。下列是改造来源及拟定变体 ID，尚未冻结；源 CSV 的行号、文件哈希、query 哈希继续沿用候选清单记录。新任务必须另记版本，不作为原版 WorkBench 成绩。

| 业务来源与拟定变体 ID | 成对条件 | 实际需要交接什么 | 要看什么 |
| --- | --- | --- | --- |
| `calendar_20` → `calendar_20_shared_queue_v1` / `calendar_20_local_queue_v1` | 后续调度请求及处理位置在公共持久队列中 / 保存在候选成员的受限工作队列中 | 队列引用、已处理位置、未处理请求标识及合法接收路由 | 备份能否自行查询恢复；交接是否减少遗漏、重复调整和额外查询 |
| `project_management_40` → `project_management_40_recoverable_v1` / `project_management_40_pending_v1` | 下一步工作可从当前任务表重新推导 / 还存在先前收到但尚未兑现的待办请求 | 未完成请求、触发条件、已做步骤和有效的业务授权依据 | 是否遗漏“尚未写入任务表”的承诺；备份自行询问或重查的代价是多少 |
| `email_53` → `email_53_review_backup_v1` / `email_53_review_unique_v1` | 已有另一位合格且独立的审核者 / 没有合法替代审核者 | 待审事项、审核职责归属及与执行者分离的约束 | 可替代时是否交接后退出；不可替代时是否保留；合法业务能否继续 |

队列中的请求、授权和待办必须来自前半段真实执行，而不是在退出时突然贴上“该节点很重要”的评测标签。业务可以出现“已经完成当前写入，但还在等后续事件”的阶段，此时观察到低产出，并不等于剩余职责已经消失。

**允许直接删除组自行恢复。** 同一变体中的五组拥有相同工具权限、查询入口、重试规则和总执行预算。若业务环境允许备份重新查询队列、重新订阅或向请求者澄清，这些恢复方式也必须向直接删除组开放，并计入成本。不能额外设置“没有调用我们的 handoff 就禁止操作”的检查。

三组共六个变体；若后续采用五组对照、每个变体一遍，将是 30 次退出决定后的新任务执行。这里仅给出上限内的规划；本文未启动后续实验，也不扩展到 75 次或全量 WorkBench。

## 交接要成为真实操作

建议增加一份结构化的运行状态，记录：

- **职责：** 谁负责接收哪类请求，哪些工作尚未完成。
- **状态：** 工作队列、游标、待办、处理记录及所依赖的证据引用。
- **资格：** 哪些现存成员原本就能合法接手；审核者与执行者是否必须不同。

交接执行顺序为：暂停候选接收新工作 → 为合格接手者复制必要状态 → 接手者确认状态可读、工具可用 → 切换接收路由 → 退休候选。失败则恢复原状态和原路由。交接不能增加工具权限，也不能把受限内容广播给全体成员。

对于受限状态，原生消息、artifact、evidence ledger、digest 和工具日志进入 prompt 的路径都要遵守同一可见性规则。独立 evaluator 可以保存完整轨迹；这些完整轨迹不能作为团队的公共记忆。

## 审核实验同时检查业务能不能完成

两个审核变体中，都安排以下后续请求：

1. 一个规则允许直接完成的普通操作。
2. 一个需要独立审核、审核通过后应当完成的操作。
3. 一个规则明确不允许的请求，作为拒绝能力检查。

三种请求都在退出决策后发布。所有组使用相同审核规则和工具后端，审核与执行不能由同一身份同时承担。

第一版采用后端强制验证有效审批的本地虚拟工具。分别记录缺少审核、被拦截的尝试、实际状态变化，以及应当成功的普通和已授权操作是否完成。若后端阻止了所有违规，就只报告拦截和业务连续性结果，不声称已经观察到实际越权减少。全部拒绝不能得到任务成功分。

如果后续要检验“退出是否真的增加违规动作”，需另设明确标注的离线模拟条件：工具后端允许虚拟状态变化，独立评测按既定审批规则判断实际动作是否合法。五组使用完全相同的后端，不能只对直接删除组取消拦截。这个条件与强制审批条件分开报告，且不连接真实发送或业务系统；它不在本轮已运行结果中。

## 对照与记录保持一致

仍比较保留、直接删除、简单保护、检查不交接、检查并交接五组。每个变体先生成一次通过检查的退出前执行状态，再复制为五个分支。所有组收到相同的新请求和外部事件，在相同轮数和预算下执行退出后的新任务。

冻结记录至少包含：

- 原始 benchmark task ID、源 CSV 0-based 行号、原始 query 与哈希。
- 新变体 ID、成对条件、候选 ID、接手者资格、拓扑及退出时机。
- 完整 checkpoint 哈希和每个分支的恢复校验结果。
- 决策前可见信息清单；决策后才生成的请求及其独立 evaluator 文件。
- 源码版本、模型配置、调用和 token 上限、停止条件。

只比较实际后续工具状态。成本包含检查、状态迁移、确认、备份重新查询和失败重试；任务完成率、重复动作、误保留、误删除及被拦截行为分别报告。先固定候选和拓扑，把交接效果测清楚；本轮不同时加入自动组队和学习型候选提名。

## 代码修改顺序及推进门槛

日历开发日志还显示，多名成员会重复读取同一事件字段。可先增加按业务状态版本缓存的公共工具结果：写入或新事件发生时立即失效，只向原本可见的成员复用。任务完成判断必须依据真实工具回执和当前状态，不能依据某个成员声称“已经完成”而提前停止。这个优化应同样应用于五组，并单独记录节省的读取与模型请求，避免把通用执行优化算成交接方法收益。

1. **先做可见性隔离。** 为 agent 状态和证据标记合法读者，修正全局 digest 的跨节点暴露；离线证明未授权成员在消息、摘要和工具输出中都看不到受限状态。此项不通过，停止后续 API 实验。
2. **再做状态与职责交接。** 实现待办和游标的快照、合法复制、接收确认、路由切换及失败回滚；验证分支互不影响、不丢待办、不重复副作用、权限不扩大。
3. **补独立评测和成对变体。** 冻结上述来源 ID 与实际变体定义；由独立 evaluator 根据退出前已发生的请求和后续事件计算期望状态，控制器不读取故障标签或未来答案。
4. **先运行一组成对案例的 API 冒烟。** 若出现数据类型、恢复、信息泄漏或评分错误，停止并保留失败记录，修复后使用新版本重跑。不能把环境错误记为方法失败，也不能只挑成功分支继续。
5. **再决定是否完成三组成对案例。** 只有退出前状态可复用、各组信息边界正确、判分能拒绝旧答案和无操作、实际开销处于预设预算内，才推进剩余小批次。

研究结果不设“完整方法必须赢”的门槛。若直接删除能够同样完成且成本更低，应明确记录：当前业务状态足够公开，显式交接没有展示额外价值。若交接减少失败但成本更高，应测量剩余工作长度和恢复次数，而非隐藏交接开销。若方法始终保留节点，则还没有证明能有效利用可替代职责。

本轮完成后的决策依据是：**哪些真实职责需要迁移，哪些状态可以便宜地重建，迁移在什么条件下值得做。**
